# E2E Failure Analysis Rubric

The single source of truth for how to categorize and reason about an e2e test failure. Two consumers share this file and MUST stay in sync:

- the **e2e-failure-analyzer skill** (`SKILL.md`, Step 7) -- interactive, run-centric triage, and
- the **e2e-failure-analyzer GitHub Action** (`analyze.mjs` injects this file verbatim into the model's system prompt).

Edit the rubric here and both consumers pick up the change. Keep it runner-neutral: output format and orchestration (which scripts to run, how to present results, what follow-ups to offer) live in each consumer, not here.

## For each failure (or group of related failures), determine

1. **Root cause category** -- one of: flaky test | infrastructure issue | product regression | locator drift / stale selector (test maintenance) | test environment issue | timeout | test logic bug
2. **Brief explanation** -- 1-2 sentences citing specific evidence from screenshots, the trace timeline, the error-context page snapshot, or logs. For a dismissal (flaky / timeout / infrastructure / test environment) or a *suspected* product regression, also state the confidence and the cited mechanism or missing evidence, per "Default to product regression until a dismissal is earned" below.
3. **Suggested action** -- what a developer should do next.

`timeout` is a last resort, not a default for anything that timed out. A `timedOut` status is a symptom, not a mechanism -- work through the sections below first; most timeouts resolve to **flaky test** (timing/interleaving), **test logic bug** (duplicated logic drift, over-broad selector), **infrastructure issue** (startup/runner slowness), or **product regression** (the awaited state never arrived). Only land on bare `timeout` when the evidence (trace, error-context snapshot, logs) genuinely gives no further signal to attribute it to one of those.

**`infrastructure issue` vs. `test environment issue`:** infrastructure issue is about the CI runner/harness itself failing to produce a usable app (startup timeouts, resource exhaustion, network flakiness to CI services). Test environment issue is about shared *test-owned* state going bad mid-run in an otherwise-healthy app (the shared workspace directory, a fixture another worker's teardown deleted). If the workbench never came up, it's infrastructure; if the workbench is fine but the file/fixture it's operating on was mutated by something else, it's test environment.

## Default to product regression until a dismissal is earned

A triage verdict routes human attention, and the expensive error is a real regression waved through as "flaky": the retry goes green and no one looks again. So the dismissive categories -- **flaky test**, **timeout**, **infrastructure issue**, **test environment issue** -- are claims that must be EARNED with specific, cited evidence of their mechanism, not reached as a fallback because nothing else was proven. Hold them to the same standard `timeout` is held to above.

- To call a failure **flaky**, cite the timing/interleaving mechanism (an element present-then-dismissed in the DOM-presence section, a race visible in the trace, a `:soft-fail` tag). "Passed on retry" or a flaky-looking history is NOT itself a mechanism -- a latent product bug also passes on retry and also looks flaky (see "Latent defects surface as flakes").
- To call it **infrastructure** or **test environment**, cite the affirmative signal (the workbench never came up; an OOM/network error in the logs; a passing sibling plus a `git clean` teardown race).
- **`test logic bug` is NOT a dismissal.** It names an owner (whoever maintains the test) and a concrete fix, so the "earn it" bar above does not apply to it -- and a cited test-side mechanism OUTRANKS the residual below rather than losing to it. A useful self-check: if your suggested action is "harden the test to wait for X," then the mechanism you actually found is test-side, and the root cause must say so. Labeling such a failure a product regression while recommending a test fix contradicts itself and routes it to the wrong owner. This does NOT extend to **locator drift / stale selector**, which keeps its own stricter decision procedure below -- permission to reach a test-side verdict is not permission to blame the selector.
- When no dismissal is affirmatively supported, the locator-drift decision below does not resolve to a stale selector, AND no test-side mechanism is supported (see "Verify the test established its own precondition" and "Account for the whole wait window"), the residual is a **suspected product regression** -- not "flaky." Say so, label it with your confidence, and name the one piece of evidence that would confirm or refute it (e.g. "suspected product regression (low confidence) -- confirm by checking whether the triggering command fired in a fuller console log" or "-- refute by finding the stable label under different markup"). This is a confidence-qualified use of the existing **product regression** category, not a new category.

This raises the bar for a *dismissal*; it does NOT lower the bar for a **confident** product-regression call, and it does NOT weaken the locator-drift decision or the "Action fired but nothing rendered" gate below. `NEVER present` alone still does not earn a confident product-bug verdict -- absent the command-fired signal or a confirmed-absent stable label, the strongest honest read is *suspected*, awaiting the confirmation you named. Only the residual changes: an unexplained failure now defaults to *suspected product regression awaiting confirmation* instead of to "flaky."

## Read the evidence before concluding

This list is priority order, not just topic grouping -- for a locator/visibility/count/text failure, start at the error-context snapshot, not the bottom.

- **Error-context page snapshot -- read it FIRST for any failure where a locator was not found, an element was "not visible", an element count was wrong, or a text/attribute assertion failed.** This markdown (`errorContextPath` on each attempt) holds Playwright's accessibility-tree snapshot of the page AT THE MOMENT OF FAILURE -- including content inside same-origin webview iframes -- plus the failing selector and the relevant test source. It is the single best evidence for telling a stale test selector apart from a real product bug. A screenshot CANNOT make this distinction: "the element failed to render" (product bug) and "the element rendered as different markup" (the test's selector is stale) look identical in a JPEG.
- **Aria-live / status announcements inside that same snapshot are ground truth about the app's internal state, not just its visible markup.** Frameworks like dnd-kit, and Positron's own components, emit `status`/`alert` regions describing what they just decided (e.g. "Draggable item 0 was dropped over droppable area 11"). When the test's own error message disagrees with what a status line says actually happened, believe the status line -- it is the product narrating its real state, whereas the test's assertion is one specific (and possibly wrong) way of checking it. Don't skim past these as UI noise; grep the snapshot for `status`/`alert` roles whenever the failure is a timeout or "condition never became true" and the mechanism isn't obvious from the DOM structure alone.
- **Screenshots:** read every screenshot for an attempt, in chronological order (the last is the failure-state; earlier frames show the moments leading up to it). Comparing them often reveals the real root cause -- the failure message and the final frame can mislead on their own. When reading them as files, read all of them in parallel in a single message.
- **Trace timeline:** read the full action sequence (selector clicks, navigations, waits) provided with each attempt. It often shows where the test actually went wrong even if the final error points elsewhere -- don't stop at the last action.
- **DOM presence + console digest (appended to the trace timeline).** Two derived sections accompany the timeline when the trace carries the data:
  - **DOM presence** answers, for the failing selector's structural class/id token, whether it *ever* matched a frame snapshot. `present in N/M snapshots (t=..)` means the element WAS in the DOM, so a visibility/timeout error is a timing or dismiss race, not a never-render. `NEVER present in any snapshot` rules out render-then-dismiss (the moment-of-failure error-context snapshot cannot -- it is a single instant) but is **ambiguous on its own**: the exact class never matched, which fits BOTH a never-rendered element (product open-path bug) AND locator drift (the element rendered under different markup -- the class is exactly the part that drifts). Disambiguate with the console digest and the error-context snapshot's stable text/label; do not read `NEVER present` as a product bug by itself (see "Action fired but nothing rendered").
  - **Console digest** lists command executions and runtime-startup phase transitions near the failure. A `CommandService#executeCommand <id>` line proves the triggering command actually *fired* (so the click was received and dispatched) -- if the target UI still never rendered (see DOM presence), the defect is in the command's handler, not the click or the environment. Startup `Phase changed to 'complete'` immediately before the failing action is a classic timing-race signal (a handler that behaves differently depending on whether discovery finished).

## Respect the clock: an effect cannot precede its cause

Each console-digest line is tagged `[before action]`, `[during wait]`, or `[after deadline]`, relative to the failing action's wait. **A line tagged `[after deadline]` was emitted after the assertion had already failed, so it CANNOT be the cause of that failure** -- no matter how much it looks like one.

This matters because the most convincing-looking error in a digest is often produced by the test's own cleanup. A `finally` block that signs out, resets a setting, or closes a workspace runs *immediately after* the failure and makes the app emit exactly the kind of alarming message a triage pass wants to blame (`... is temporarily unavailable`, `session expired`, `disconnected`). Attributing the failure to it inverts cause and effect and sends the fix to the wrong team.

Before citing any log line or console line as the mechanism of a failure:

- **Check its phase tag** (console digest) or **its timestamp against the window header** (log excerpt). Only `[before action]` and `[during wait]` events are candidate causes.
- **If the only supporting evidence is `[after deadline]`, the dismissal is not earned** -- fall back to the residual rule in "Default to product regression until a dismissal is earned."
- **Read the failing test's `finally`/teardown** (and any `afterEach`) before blaming a post-deadline event on the product. If the test tears down the very thing the message is about, the message is fallout from the test, not a product or environment fault.
- **Failing test source:** read it before drawing conclusions. The source tells you what the test intends to verify, which page objects/helpers it depends on, and the setup steps -- often the difference between "the assertion is the bug" and "setup failed before reaching the assertion." Test source lives at `test/e2e/<file>` (the Action exposes the checkout as `<REPO_ROOT>`; interactively it is your working tree). When the test imports from `../../pages/`, `../../fixtures/`, or `../../infra/`, read those too if the failure involves their behavior. `infra/` (`workbench.ts`, `code.ts`, the Playwright drivers) is especially useful for failures during workbench startup, session creation, or teardown.
- **Sibling tests in the same file ("Other tests in this file: ..." in the input).** Before blaming setup/fixtures, check whether a sibling test PASSED. If the failing test depends on a fixture created in `beforeAll`/global setup and a sibling passed using that same fixture, setup succeeded and the fixture WAS provisioned -- so the failure is something mutating or removing the fixture mid-run, NOT "setup never ran." A "file not found" with a green sibling is a lifecycle/race, not a provisioning failure. The same signal applies beyond fixtures: if a passing sibling -- a parametrized entry in the same loop/`test.each`, or another test -- exercises the SAME assertion or page-object method that failed here, that shared code is not universally broken. Diagnose what the failing case does differently (an extra editor opened first, a different precondition, a different platform) rather than blaming the shared assertion.
- **Log excerpt ("Log excerpt (attached logs, sliced to the failure window)" in the input).** The run's kernel/runtime/extension/runner logs, time-sliced to the failing action's wait. It carries detail the screenshot and Playwright error cannot -- a kernel's resolved file path, an expired-credential message, a stack trace. A screenshot of "No such file" looks identical whether the file was never created or was deleted after creation; the log line (and the passing sibling) is what tells them apart. Read it for any environment/fixture/startup failure. Two properties to use deliberately:
  - **All severities are included, and an `[info]`/`[debug]` line is often the decisive one.** A success line inside the window (e.g. `[anthropic] Fetched 11 models from API`) positively REFUTES an "external dependency was unavailable" theory. Do not treat "no errors in the logs" as "no evidence in the logs" -- the absence of errors alongside a successful-looking startup sequence is itself evidence that the backend was healthy and the defect is downstream (rendering, wiring, the webview).
  - **The "went quiet before the deadline" section is positive evidence, not missing data.** A log that stops emitting at the moment the UI should have appeared and stays silent for the rest of the wait means the component stopped doing work -- it was not retrying, not erroring, just idle. Combined with a widget that never rendered, that points at the product (something never got kicked off, or a render path died silently), not at the environment.

### Account for the whole wait window, not just its end

The same clock discipline applies to where a wait BEGAN. The failing action's timeout is a budget, and a budget can be spent on something other than the thing being awaited -- so before concluding the product was slow to render, establish what the app was doing when the wait opened.

- Read the timeline backwards from the failing action to the test action that triggered it. If a window reload, workspace switch, or workbench restart falls between them, the wait is paying for that too.
- Subtract it. Runtime-startup phase transitions in the console digest bound this precisely: a `Phase changed to 'starting'` / `'newFolderTasks'` line landing 23s into a 40s wait means 23s of the budget went to reload and the product had ~17s left to do the awaited work.
- A "slow open path" or "handler awaits something before showing its surface" verdict requires the wait to have begun when the app was already in a position to render. When most of the budget was consumed before that point, the finding is an **under-budgeted wait in the test** (`test logic bug`), and the fix is to wait for the intervening phase to finish first -- so each wait gets its own budget -- rather than widening the timeout or opening a product issue.

## Locator drift vs product regression

Whenever a locator did not match, decide between **locator drift / stale selector** (test maintenance) and **product regression** using the error-context page snapshot:

- Take the target's STABLE, human-meaningful identifier from the failing selector -- its visible text, placeholder, aria-label, or role name -- NOT the structural class/id, which is the part that drifts.
- Identifier **present but under a different role/shape** than the selector expects (e.g. the selector wants `textarea[placeholder="X"]` but "X" now appears as a generic/div, or a labeled control changed tag or moved) => **locator drift / stale selector**. The element exists; the selector is stale (usually NOT a product bug). Confirm against the page object in `test/e2e/pages/*.ts`: if its selector targets markup that no longer matches the snapshot, it is stale, and the action is to update the selector.
- Identifier **absent entirely** (no equivalent affordance present) => **product regression**: the element genuinely failed to render.
- Element **present with its expected role** but the error is a visibility/interactability timeout => a timing failure, not locator drift. Work out WHICH timing failure before settling on **flaky test**: check where the wait began (see "Account for the whole wait window, not just its end") -- an under-budgeted wait is a `test logic bug` with a specific fix, not a flake to retry.
- **Locator drift is deterministic, so an intermittent failure is not drift.** Markup does not revert between runs: if a selector stopped matching the product, the test fails on EVERY run on the affected platform. A test that mostly passes and occasionally fails on the same selector demonstrably matches that selector when it passes, so "stale" cannot be the mechanism. Read the per-environment pass rate before concluding drift -- a high pass rate refutes it outright -- and treat any wording you find yourself reaching for like "sometimes renders under drifted markup" as a sign the verdict is being forced. Likewise, if the failure-state screenshot shows the target rendered WITH the text or label the selector filters on, the selector was looking for exactly that element: the question is timing, not markup.
- A **matched** locator is not proof until you confirm it matched the element the test MEANS. A broad selector (`getByLabel`/`getByText`/`getByRole`, or a container selector not scoped to one editor group / tab / dialog) can resolve to a leftover view, a duplicate control, a notification, or a second editor group -- an element the test never intended. When the call log shows the selector DID resolve (even repeatedly) but the failure is "not visible" / wrong-count / wrong-state, check WHICH surface owns the matched node before concluding the assertion is inverted. If it belongs to another surface, this is a **test logic bug (over-broad selector)** and the fix is to scope the selector, not to flip the assertion.
- Markup can drift from code that is NOT in the head commit -- a bootstrapped extension floated to its latest build at test time (e.g. Posit Assistant), upstream-merged code, or remotely-served content -- so an unrelated-looking commit does NOT imply product regression. Check the snapshot for changed markup before concluding either way (see "Check the triggering commit").

## Action fired but nothing rendered (product open-path bug, not environment)

When a click/keypress "does nothing" -- the action itself succeeds in the trace but the expected UI never appears -- do NOT default to "environment flake." Cross-reference the two derived trace sections:

- If the **console digest** shows the triggering `CommandService#executeCommand <id>` fired (often repeatedly, once per retry) AND the **DOM presence** section shows the expected widget was `NEVER present`, the command's handler ran but failed to render its UI. That is a **product regression** (categorize it as such even when the head commit is unrelated -- the defect is latent, see below), not "test environment issue" and not "infrastructure."
- A frequent shape: the handler `await`s something slow (an extension-host RPC, interpreter discovery, a network call) *before* showing its surface, so on a slow/first-load runner the surface never appears within the test's budget. The `Phase changed to 'complete'` timing line landing just before the failing action is a strong tell.
- This is distinct from a **blur/dismiss** race, where DOM presence shows the widget *did* appear (in some snapshots) then went away. Use the DOM-presence section to tell them apart -- a screenshot cannot.
- **`NEVER present` alone is NOT enough to call this** -- the DOM-presence section keys on the selector's structural class, which is exactly the part that drifts, so a stale selector (locator drift: the element rendered under different markup) also shows `NEVER present`. Require the command-fired signal from the console digest, OR confirm via the error-context snapshot's *stable text/label* that the affordance is genuinely absent (per "Locator drift vs product regression"), before concluding product open-path. A `NEVER present` with no command-fired line and a matching stable label in the snapshot is locator drift, not a product bug.

## Verify the test established its own precondition (a "test logic bug" sub-case)

When the mechanism is "state X was not true even though the test set X up," do not jump to a product-side detection race. Read the setup helper and ask what it actually waited for. A test that raced its own setup is a **test logic bug**, and the evidence is usually already in the trace timeline you have.

Two shapes account for most of these:

- **Asserting on output that marks the START of an async operation rather than its completion.** A package install, a build, a clone, a download all print their first line immediately. A helper that submits the command and then waits for text like `/Installing|Downloading|Fetched/` has proven the operation *began*, nothing more.
- **A "readiness" check that is not an idle gate.** Waiting for a console prompt character proves little if the prompt stays rendered while the runtime is busy. Any readiness check that returns in tens of milliseconds has told you nothing about work that takes seconds.

Time the setup step from the trace timeline's `[before]`/`[after]` timestamps and compare it against how long that operation plausibly takes. If setup "completed" in far less time than the work it was supposed to await -- e.g. an R package install where the readiness check returned in 37ms and the whole step took 5s -- the test moved on mid-operation, and any window reload or session restart that follows kills the work in flight. The state the next step then observes is genuinely wrong, so a product check reporting that state (a "package not installed" prompt, a missing-file error) is **correct behavior**, not a detection bug. Note that this failure mode is intermittent by nature: it is a race the test sometimes wins, so a high pass rate does not argue against it.

The fix belongs in the helper: wait for a real completion signal the product already maintains (a busy/interrupt affordance disappearing, a status transition) and, where cheap, assert the resulting state before returning.

## Duplicated logic drift (a "test logic bug" sub-case)

Some test helpers re-derive a condition the product already computes and exposes, instead of asserting on the product's own signal directly -- e.g. a helper that recomputes "is this element in view" from raw bounding-box math, when the component being driven already tracks and renders its own notion of that state (a CSS class, a data attribute, a status region). When such a helper's homegrown check disagrees with the product's real state, the helper's criteria have quietly drifted from the algorithm it was standing in for -- often because the product's real logic (e.g. nearest-match collision detection) is looser or differently-shaped than the test's approximation (e.g. a fixed percentage band).

Suspect this when: the failure is a timeout/condition-never-true on a check the test invented itself (not a direct locator/assertion against product markup), AND the error-context snapshot or an aria-live status region shows the product had already reached the state the test was waiting for. The fix is not to loosen the test's thresholds -- it's to delete the re-derived check and assert on the product's real signal instead (the class, attribute, or status the component already maintains). Trace the test helper against the equivalent product source function before concluding this is the cause; the divergence is usually visible by comparing the two side by side.

## Other heuristics

- Multiple tests failing in the same file/suite usually share a root cause -- group them.
- `timedOut` status often indicates flakiness or infrastructure slowness.
- Failures during app startup (e.g. waiting for the workbench) are usually infrastructure -- BUT a *specific control* that never responds to a user action right after startup (command fired, no UI rendered -- see "Action fired but nothing rendered") is a product open-path bug, not infrastructure. Reserve the "infrastructure" read for the app/workbench as a whole failing to come up.
- Tests tagged `:soft-fail` are known flaky.
- **Shared-workspace / teardown races (a "test environment issue" sub-case).** All e2e workers share ONE workspace directory (`<tmp>/vscsmoke/qa-example-content`, cloned once in global setup; `playwright.config.ts` runs `workers: 3`). `TestTeardown.discardAllChanges()` runs `git clean -fd` in that shared dir, which deletes any untracked, non-ignored file. So a fixture a test downloads at runtime (e.g. an S3 parquet written into the workspace by a `beforeAll`) can be deleted by a *concurrent* worker's teardown mid-test. Suspect this for an INTERMITTENT "file missing / cannot open" error on a runtime-downloaded fixture -- especially when a sibling test passed reading the same file. The fix is usually to gitignore the downloaded artifact (so `git clean -fd`, which has no `-x`, skips it), not to re-check provisioning. Do NOT conclude "fixture never provisioned" without ruling this out.
- **Same-file preceding-test state leakage (a "test environment issue" sub-case, NOT concurrency).** `author-e2e-tests/references/test-structure.md` ("Parallel Test Considerations") already establishes that tests in one spec file share a worker-scoped app instance and run in file-definition order with no intra-file parallelism -- this is the diagnostic flip side: when a failure's evidence shows disruption another test in the same file plausibly causes (a window reload, a session restart/delete, a settings change), check the immediately PRECEDING test in file order, not just concurrent workers. Confirm the timeline: does the log show the disruptive event (e.g. all sessions' websockets resetting, an extension-host restart) landing right before the failure, and does the report's sibling-test list (which mirrors file-definition order) place a state-mutating test directly before the failing one? A test whose own fixture reuses shared state (e.g. `sessions.start(..., { reuse: true })`) racing against a prior test's disruptive action is a plausible root cause when the timeline lines up this way (a single run is one data point, same caveat as "Check the triggering commit" below). Where to fix it is a real choice, not a given: cleaning up in the offending test (`common-mistakes.md` #8) only protects this one adjacency, while hardening the shared reuse path against the underlying condition (a session not yet reattached, regardless of why) protects every test that hits it -- weigh which the evidence actually calls for.

## Use historical data when available

If historical test-health data is provided, use it to separate regressions from known flakes:

- 0% pass rate on one platform but 100% on others = deterministic platform regression, NOT flaky. Always read the per-environment breakdown, not just the aggregate pass rate.
- A failure pattern that starts on this run across all platforms at once points to a regression (or a change in code sourced outside the head commit, e.g. a bootstrapped extension), not a flake.
- **A rising failure rate is a regression signal, not a flake signal.** If history shows the test was reliably green and then began failing or flaking noticeably more often from some point in the window, something changed -- treat that trend break as affirmative evidence for a regression (product, or product-adjacent like a bootstrapped extension floated to latest) and try to align the inflection with a SHA range (see "Check the triggering commit"). A flat, long-standing low pass rate is a standing flake; a step change from green to intermittent-red is not -- do not fold the latter into "known flaky."
- **A "first seen" date is censored by the lookback window, so it is not automatically an onset date.** The history query covers a fixed window (`lookback_days`, currently 14), and a pattern's first-seen date can only ever fall inside it. Compare the two: a first failure at or within about a day of the window's start means earlier occurrences are simply outside the data and the onset is UNKNOWN -- do not present it as when the problem began, and do not build a regression argument on it. Only a stretch of clean runs between the window opening and the first failure supports "this started here." State the window bound either way, so a reader cannot mistake a censored date for an origin.
- **Intermittent does not mean "provisioning broke," even for "file not found" errors.** A truly missing/never-provisioned fixture fails the test EVERY run (0% on the affected platform). If the suite is mostly green with some flakes (e.g. 153/159 passing, several flaky), a "file not found" is far more likely a mid-run lifecycle/race (something deletes the file) than provisioning that never ran. Reconcile your root cause with the pass rate: a high pass rate contradicts a deterministic-missing-fixture conclusion.

## Check the triggering commit

This section assumes a single run with one head commit to check causality against. If you're instead looking at a failure pattern's occurrences spread across many SHAs over a lookback window, a single occurrence's commit diff is weak evidence either way -- use the historical spread itself: a pattern recurring across many unrelated SHAs over time argues AGAINST a fresh single-commit regression (it's a standing flake or long-lived product/test-logic bug), while a pattern that only appears on SHAs from a narrow recent window is the case where checking that window's commits is worth doing.

For tests that **failed all retries** (not just flaky), inspect the head commit's changed files and assess causality against:

- **The failing test file itself** and its page objects/helpers -- changes here could introduce a test logic bug or a stale selector.
- **Product source code exercised by the test** -- changes to the feature under test could be a real product regression the test correctly caught.
- **Shared infrastructure** (startup, layout, rendering) -- changes here could alter timing or behavior enough to surface a latent flaky test.

A commit that modifies notebook cell rendering is a plausible cause for a notebook cell-count assertion failure, even if the test has flaked before. Conversely, a commit that only changes R interpreter code is unlikely to cause a Python plot test failure. When the commit is relevant, say so explicitly, e.g. "modified `notebookCellList.ts` (notebook cell rendering) -- plausible cause" or "no files related to this test's feature area -- unlikely cause".

**Caveat -- code outside the head commit.** Not everything under test comes from the head commit. UI can be produced by extensions bootstrapped to their latest build at test time (e.g. Posit Assistant), upstream-merged code, remotely-served or CDN content, or dynamically-installed dependencies -- none of which appear in the head commit's changed files. So an unrelated-looking changed-files list is NOT evidence for or against a product regression: a failure can have a real cause that simply lives outside the commit. Decide from the page snapshot and the locator-drift decision above, not from the changed-files list.

**Latent defects surface as flakes.** A product bug introduced weeks ago (a race, an unguarded `await` before a UI shows, a platform-specific timing assumption) can start failing on an unrelated run when a timing shift or a slower runner tips it over -- and it will look "known-flaky" in history. An unrelated head commit and a known-flaky history therefore do NOT rule out a product bug. When the evidence points to a product open-path defect (command fired, UI never rendered -- see "Action fired but nothing rendered"), call it a product regression and say the head commit is not the origin, rather than downgrading it to "flaky test" or "infrastructure." A known-flaky test that also shows this product signal is an unfixed product bug wearing a flake costume -- flag it for a fix, not just a retry.

## Sanity-check the suggested action

Before recommending a fix, confirm it is consistent with the evidence you just used:

- It must keep the currently-passing sibling cases passing. A change to a shared assertion or page-object that would break a green sibling (e.g. inverting an assertion a passing case relies on) is wrong -- say why yours would not.
- When the assertion is about an element's presence or absence, check the product's intent (the feature's `when` clause, precondition, or the source that renders it) before concluding the test is wrong. The element may be present-by-design under a different precondition than the failing case set up, so "flip the assertion" can contradict how the product is meant to behave.
