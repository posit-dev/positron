Likely cause · Hypothesis

The uv provider's version step ignores the setting and offers Pythons that uv would download. In detail, pickPythonVersion (extensions/positron-python/src/client/pythonEnvironments/creation/provider/uvUtils.ts:40) lists every version from getUvPythonVersions(), downloadable ones included, and uv venv -p <version> downloads a missing one. getRankedProviders (extensions/positron-python/src/client/pythonEnvironments/creation/createEnvApi.ts:127) keeps uv in the list whenever it is installed, and the PR's test uv is still listed first when it is installed and python.allowUvPythonInstall is off in createEnvApi.unit.test.ts asserts that. The version list predates the change, but the change rewrote the setting's description to promise that Positron does not install Python with uv when it is off, and gates uv entirely in the notification path (autoCreateVenv.ts) but not here.

Change under test

The create venv from requirements.txt or pyproject.toml notification now offers uv whenever python.allowUvPythonInstall is on, and installs uv (with consent) when it is missing instead of failing. Create Environment's uv provider does the same. With the setting off, uv is left out of Create Environment while it is missing, Python: Install Python via uv is hidden, and any uv install is refused with an error that links to the setting.

Environment
  • Positron 2026.10.0 build 0, dev build of 9e0cbdf306 (Code - OSS 1.134.0), on Ubuntu 24.04.4 LTS (Linux x86_64).
  • Kernels: Kallichore 0.1.71.
  • Python 3.12.3 (system) and Python 3.14.6 picked by uv for the new venvs, with requests 2.32.3 from requirements.txt.
  • Each scenario runs in its own Positron instance launched for this run with HOME pointed at an empty folder and /root/.local/bin and /root/.venv/bin dropped from PATH, so uv reads as not installed. The official uv installer writes uv into that empty home. Seed profile holds only the harness dialog settings.
State manipulation

Each scenario group ran in its own Positron instance launched for this run (four in all, on CDP ports 40783, 37799, 46133 and 38751, each stopped afterwards), with HOME pointed at an empty folder under the run directory and /root/.local/bin and /root/.venv/bin dropped from PATH, so uv read as not installed. The real uv installer wrote uv into that empty home. For the install failure, a curl stand-in that fails to resolve the host was put first on PATH, then deleted to remove the fault. python.allowUvPythonInstall was set through a seed settings file and through the Settings editor and user settings.json. Nothing outside the run directory was changed. The launcher's own CDP check uses curl, so it timed out for the instance with the failing curl, which was attached by hand. The pre-launched instance was not driven.
